# Tirelo Services — PostgreSQL Performance Report

_Phase 16 deliverable. Generated and analysed from the committed benchmark run
([`benchmark/reports/benchmark-small.md`](../benchmark/reports/benchmark-small.md)).
Re-run with `npm run bench` to refresh; larger sizes via
`node benchmark/scripts/run-all.js medium|large`._

## 1. Executive summary

PostgreSQL is **production-ready** for Tirelo Services. Across CRUD, search,
marketplace workloads, concurrent load and payments it delivered sub-millisecond
to low-single-digit-millisecond latency at the baseline dataset with a **0%
error rate** at every concurrency level tested. The repository abstraction is
unchanged — the same code runs on PostgreSQL, MongoDB or the in-memory store —
so this is a configuration choice (`DB_DRIVER`), not a rewrite.

Key results (small dataset: 1,000 users / 500 providers / 5,000 bookings):

- **Reads are index-served.** Every hot list/lookup path (bookings, transactions,
  reviews, notifications, messages, audit by-owner-newest) uses a composite or
  partial index — p50 **0.03–0.06 ms**, p95 under **0.4 ms**.
- **PostgreSQL beats the in-memory repo on ordered list queries** (`listByUser`:
  **3,492 vs 2,262 ops/s**) because the composite index serves the sort while the
  in-memory store full-scans and sorts in JS.
- **Throughput scales cleanly with concurrency** to ~**5,400 ops/s** on a 4-vCPU
  box, errors stayed at 0 through 500 concurrent clients.
- **Payments are correct and fast.** `createPayment` p50 **2.2 ms**, webhook
  settle **1.5 ms**; idempotency holds under sequential retries and the terminal
  state is correct under parallel retries — all without touching the payment
  module.
- **Operations are quick.** Whole-DB `ANALYZE` 233 ms, `VACUUM (ANALYZE)` 257 ms,
  `pg_dump` 303 ms, restore into a scratch DB 679 ms.

## 2. Methodology

- The benchmark drives the production **repository layer** (the exact methods
  services call), not hand-written SQL, so access patterns match the app.
- Datasets are generated by a **seeded RNG** (reproducible) with realistic
  Botswana geography (population-weighted across Gaborone, Francistown, Maun, …)
  and a coherent relational graph (bookings → transactions/reviews/conversations,
  customers → favourites/addresses, etc.).
- Latency uses `process.hrtime.bigint()`; percentiles are nearest-rank on the
  full sample. Each micro-benchmark warms up before measuring.
- Query plans use `EXPLAIN (ANALYZE, BUFFERS)` after a fresh `ANALYZE`; index
  availability is **validated** by re-planning with `enable_seqscan=off`.
- Full harness + how-to: [BENCHMARKING.md](./BENCHMARKING.md).

## 5. MongoDB vs PostgreSQL

Both are first-class drivers behind the identical repository interface, so
switching is a config flag with no code change. PostgreSQL was chosen as the
production default because: strong relational integrity for the
bookings↔payments↔reviews graph; rich indexing (composite, partial, GIN on
JSONB) that the benchmark shows serving every hot path; mature backup/PITR; and
SQL aggregates for analytics. The JSONB `doc` column preserves the schema
flexibility that made MongoDB attractive. Run the suite with a Mongo URL to
populate a side-by-side table for your hardware.

## 6. In-memory baseline

The in-memory repositories are the **upper bound** for point-operation latency
and are used by the test suite (no DB needed). They are not durable, not shared
across instances, and degrade on scans/sorts (no indexes) — see `listByUser`
above. Useful as a ceiling and for fast CI, not for production.

## 7. Query analysis & indexing (Phase 6/7/8)

After `ANALYZE`, the representative repository queries planned as:

- **Index-served (p50 0.03–0.16 ms):** booking list-by-customer & by-status,
  transaction list-by-customer, review list-by-provider, notification unread
  count (partial index) and list, message history, audit by-action — all on the
  new composite/partial indexes.
- **Seq scan but validated index path:** provider filters (500-row table — a scan
  is genuinely optimal at that size; `idx_providers_category`,
  `idx_providers_categories_gin`, `idx_providers_availability` confirmed usable)
  and the `count`/`sum` aggregates (which must read all matching rows; the
  status composite index is confirmed available for selective variants).

**Indexes added** (additive, idempotent, in `src/db/schema.sql`):

- `providers`: `availability_status`, `starting_price`, and a **GIN index on
  `doc->'categories'`** so multi-category containment (`@>`) is index-backed.
- Composite `(owner/status, created_at DESC)` on bookings, transactions, reviews
  so filter **and** sort are served by one index.
- `notifications`: `(user_id, created_at DESC)` + a **partial index
  `WHERE read=false`** for the very hot unread-count/list path.
- `messages (conversation_id, created_at)`, `conversations` by participant +
  `last_message_at`, `audit_logs` by actor and `(action, created_at DESC)`.

**Redundant indexes removed:** the single-column `idx_bookings_customer/provider/
status`, `idx_transactions_customer/status`, `idx_reviews_provider`,
`idx_notifications_user`, `idx_audit_action` — each is fully covered by a
composite whose leading column answers the old equality lookup. This lowers
write amplification and storage with no read regression.

### JSONB strategy

Filter/sort keys (`status`, `customer_id`, `provider_id`, `category`,
`created_at`, `rating`, `starting_price`) are **promoted to indexed columns**;
the full domain object stays in the `doc` JSONB column for flexibility.
Multi-value attributes (`categories`) stay in JSONB with a **GIN index**. This
balances relational performance with document flexibility. Promote a field to a
column only when it becomes a hot filter/sort key.

## 9. Concurrency & connection pool (Phase 5/9)

Mixed ~80/20 read/write workload:

| Concurrency | ops/s | p50 | p95 | p99 | errors |
| --- | --- | --- | --- | --- | --- |
| 50 | 3,860 | 12.98 | 18.55 | 21.30 | 0 |
| 100 | 5,020 | 18.88 | 26.72 | 28.46 | 0 |
| 250 | 5,408 | 45.68 | 50.32 | 51.81 | 0 |
| 500 | 5,141 | 94.64 | 106.46 | 108.64 | 0 |

Throughput rises and plateaus around the core count × saturation point; latency
grows linearly with concurrency (expected queueing) with **zero errors**. The
pool sweep (SELECT workload, 64 clients) favoured **pool max 20–40** on this
4-vCPU box.

**Recommendation:** size the per-instance pool at roughly **(vCPUs × 2) + a small
spare** (≈10 on this box; 20–40 on larger nodes), and set the database
`max_connections ≥ instances × pool + headroom`. Put PgBouncer in front for many
app instances. Re-run with `BENCH_CONCURRENCY="100,500,1000,5000,10000"` on
production hardware for go-live sign-off.

## 10. Payments (Phase 11)

Through `PaymentService` only — the payment module is unmodified.

| Operation | p50 (ms) | p95 (ms) | ops/s |
| --- | --- | --- | --- |
| createPayment | 2.17 | 2.52 | 453 |
| getByReference | 0.24 | 0.30 | 4,088 |
| webhook settle | 1.49 | 1.74 | 660 |
| listForCustomer | 0.39 | 0.52 | 2,497 |

- **Sequential idempotency: PASS** — 10 replays of a settlement webhook leave the
  transaction `succeeded` with exactly **one** settlement event.
- **Parallel retries (25 simultaneous):** 0 errors; the persisted document ends
  with the correct terminal status and a single settlement event (JSONB
  last-write-wins keeps one writer's snapshot).
- **Hardening note:** that is last-write-wins, not row-level serialization. If a
  future change makes the webhook take an external side effect *per call* (e.g. a
  payout), guard it **at the repository layer** (`UPDATE … WHERE status NOT IN
  (terminal)` or `SELECT … FOR UPDATE` in a transaction) — no payment-module
  change required.

## 13. Scaling recommendations

1. **Vertical first:** PostgreSQL is CPU/IO bound here; more vCPU + tuned
   `shared_buffers` (~25% RAM) and `work_mem` lifts throughput immediately.
2. **Read replicas** for analytics/admin aggregates as they grow; route reports
   off the primary.
3. **PgBouncer** (transaction pooling) once you run several API instances.
4. **Cache** hot, rarely-changing reads (categories, provider cards) in Redis —
   the app already has a cache abstraction; see Phase 10 note below.
5. **Partition** `bookings`/`transactions` by month only if/when single-table
   size makes vacuum/index maintenance painful (not before tens of millions).

## 14. Caching strategy (Phase 10)

The app ships a cache abstraction (`CacheService`, Redis or in-process) and a
`responseCache` middleware already used on public GETs. Recommended targets and
TTLs: service categories (1 h), provider cards / discovery first page (30–60 s),
admin dashboard aggregates (30–60 s), analytics rollups (5–15 min). Measure hit
rate via the cache backend; the biggest win is the admin aggregate bundle
(Phase 4: ~3.4 ms × every dashboard load).

## 15. Disaster recovery observations

`pg_dump`/`pg_restore` are fast at this scale and already wired into
`deploy/backup.sh` (custom format) and `docs/DISASTER_RECOVERY.md`. Pair nightly
logical dumps with managed snapshots; rehearse restores quarterly. RPO ≤ 24 h
(snapshots) / RTO ≤ 1 h (redeploy image + restore) remain realistic.

## 16. Production tuning checklist

- [ ] `shared_buffers` ≈ 25% RAM; `effective_cache_size` ≈ 50–75% RAM.
- [ ] `work_mem` raised enough that hot sorts stay in memory (watch for external
      sorts in `query-analysis`).
- [ ] Per-instance pool ≈ (vCPU × 2) + spare; `max_connections` ≥ instances ×
      pool + headroom; PgBouncer for many instances.
- [ ] `wal_level=replica`, archiving/PITR configured; at least one replica.
- [ ] Autovacuum on; tighten scale factors for the largest tables if bloat shows.
- [ ] Nightly `pg_dump --format=custom` (deploy/backup.sh) + managed snapshots;
      quarterly restore test.
- [ ] `postgres-exporter` scraped by Prometheus (see `docs/MONITORING.md`); alert
      on connection saturation, replication lag, slow queries, disk.
- [ ] Re-run `npm run bench medium`/`large` on production-class hardware before
      go-live and capture the report.
- [ ] Redis enabled for shared cache + rate limiting in multi-instance deploys.
