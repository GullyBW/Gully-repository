# Benchmarking guide

How to run, extend and interpret the PostgreSQL benchmark suite
(`benchmark/`). For the analysed results and tuning recommendations see
[PERFORMANCE_REPORT.md](./PERFORMANCE_REPORT.md).

## What it measures

The suite drives the application's **real repository layer** (the same methods
services call), so numbers reflect production access patterns rather than
synthetic SQL. It covers the brief's phases:

| Phase | Scenario | What it answers |
| --- | --- | --- |
| 2 | `lib/seed.js` | reproducible datasets (small/medium/large), Botswana geo |
| 3 | `repository-crud` | CRUD latency/throughput, PostgreSQL vs in-memory vs Mongo |
| 4 | `workload` | latency behind customer/provider/admin actions |
| 5 / 9 | `concurrency` | percentile latency under load + pool-size sweep |
| 6 / 7 / 8 | `query-analysis` | EXPLAIN ANALYZE, index validation, JSONB strategy |
| 11 | `payment` | payment latency + idempotency (module untouched) |
| 12 | `search` | provider-discovery filters + ranking |
| 14 | `operational` | backup/restore/vacuum timings |
| 15 | `dashboard/` | browseable results + trend comparison |
| 16 | `PERFORMANCE_REPORT.md` | the analysed write-up |

## Prerequisites

- Node 20+ and the project dependencies (`npm ci`).
- A reachable PostgreSQL. Locally: `docker compose up -d postgres` (the project
  compose file), or any instance via `BENCH_DATABASE_URL`.
- Optional: a MongoDB for the comparison (`BENCH_MONGODB_URI`).

## Running

```bash
npm run bench                 # full run, "small" dataset (the committed baseline)
node benchmark/scripts/run-all.js medium      # larger dataset
node benchmark/scripts/run-all.js small --only=query,search
npm run bench:seed -- small   # just load a dataset
npm run bench:queries         # print EXPLAIN analysis for the live DB
```

Outputs land in `benchmark/reports/` as `benchmark-<size>.json` (machine
readable), `benchmark-<size>.md` (human readable) and `latest.json`. Open
`benchmark/dashboard/index.html` in a browser to explore them.

All knobs are env vars (`BENCH_SIZE`, `BENCH_SAMPLES`, `BENCH_CONCURRENCY`,
`BENCH_POOL_SIZES`, `BENCH_SEED`, …) — see `benchmark/README.md`.

## Reproducibility

Datasets are generated by a seeded RNG (`BENCH_SEED`, default `1337`), so the
same size + seed produces byte-identical data on any machine. The benchmark
unit tests (`tests/benchmark.test.js`, part of `npm test`) assert this, plus the
correctness of the statistics functions.

## Interpreting results

- **p50/p95/p99** are latency percentiles in ms; **ops/s** is sustained
  throughput. Latencies are the *database portion* of a request — add HTTP and
  serialization for end-to-end.
- In the query-analysis table, a **Seq Scan** on a small table is not a problem:
  PostgreSQL correctly prefers it when the table is tiny. The **Index path**
  column re-plans with `enable_seqscan=off` to prove an index exists and will
  take over as the table grows; recommendations are only emitted for large
  tables that lack any index path.
- The in-memory driver is the theoretical ceiling for point operations but is
  single-process and non-durable; it is a baseline, not a production option.

## Extending

Add a scenario as `benchmark/scenarios/<name>.js` exporting
`async function run(ctx)` that returns a report section
(`{ title, description?, tables?, notes? }`), then register it in
`scripts/run-all.js`. `ctx` provides `{ drivers, dataset, config, size, stats, pg }`.

## CI

`tests/benchmark.test.js` runs in the normal Jest suite (no database). A full
benchmark run is intended to be triggered manually or on a schedule against a
provisioned PostgreSQL, not on every PR, because it is time- and
resource-intensive at larger sizes.
